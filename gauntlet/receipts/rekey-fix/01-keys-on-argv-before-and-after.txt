  $ ls -l /proc/17752/cmdline /proc/17752/environ

That permission pair is the whole finding: the running service reads BOW_STORE_KEY from the
environment, which the kernel keeps to the owner; this command read the same class of secret
from the one file the kernel hands to everybody. (This container runs a single user, so the
mode bits are the evidence for the unprivileged case rather than a second shell.)

What either string is worth — the reason this is not a hygiene nit:

  session-signing secret from the OLD key: 2AiS9SbsCcMXM0vCG1b_6W0Ljrss-_AKjaeSmIf5EwU
  session-signing secret from the NEW key: jfYGvXV5033a0LnP5DLJsEQJIx_VMWRpy7r3wXRFbYE

i.e. HMAC(key, "bow.derive.v1.session") — `keeper.derive("session")`, the secret every teacher
and student token is signed with. Either key decrypts the store *and* mints tokens.

The old flags are refused by name rather than dropped in silence, because the operator
following an old runbook has to be told both what to type and that what they just typed is
already public:

  $ node .../rekey.js --from … --to … --old-key "$OLD" --new-key "$NEW"
  --old-key and --new-key are gone. A key on the command line is readable by every process on the host
  (`ps -eo args`, /proc/<pid>/cmdline) for as long as the conversion runs, and either of these keys
  decrypts the whole store and derives the session-signing secret.

  Treat any key on this command line as exposed: it is in the process table and in your shell history.
  Then re-run it the way below.
  … full usage …
  exit=2      (and the destination directory was not created)

BOW_STORE_KEY — the running service's own variable — is still not read. Property 1 of the six
is "both keys explicit, nothing inferred from the environment the service happens to be
running with", and inheriting a maintenance shell's BOW_STORE_KEY would have broken it while
fixing this. There is a test for exactly that.

================================================================================
The six properties, re-checked after the change
================================================================================

  1. Both keys explicit          — env vars / key file / stdin, named for this run; BOW_STORE_KEY ignored.
  2. Nothing mutated in place    — sha256 of every file in the source, before and after a full run:
                                     before 1f59ca3ec378cc0bf4559b955b61b0de4c5d73b0009e8a694bd26fa5fb11197c
                                     after  1f59ca3ec378cc0bf4559b955b61b0de4c5d73b0009e8a694bd26fa5fb11197c
  3. Every record verified       — unchanged code path; unreadable-record abort still exercised by test.
  4. Canary planted last         — unchanged, and a refused dirty destination gets no canary (receipt 02).
  5. Reversible                  — source untouched (2); old key still opens it.
  6. Resumable                   — a finished destination minus one record: "1 converted, 5999 already done".
